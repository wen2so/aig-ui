# aig-ui 实施排期与验收

本计划落实[实施方案](./implementation-plan.md)、[加载动效规范](./motion-system.md)和[AI 复用规范](./ai-reuse-spec.md)。当前只交付方案文档，以下代码、脚本、测试记录与发布产物均为待实施任务。

## 1. 交付范围与资源假设

v1.0 包含 M0 动效核心 2 个组件族、G0 通用基础 17 个、G1 业务通用 23 个、A1 AI 交互 8 个，共 50 个组件族，以及 5 个可编辑页面组合。部件、内部辅助函数和样式配方不重复计数。

排期基于 2 名前端工程师全职、1 名设计师约半职、1 名测试人员约半职，具有 React 与组件库经验，使用成熟交互基础。工程工作量初估 132–164 人日，增加约 20% 集成与修正缓冲后为 158–197 人日，对应约 16–20 个工作周。该估计不包含等待外部账号、授权和业务反馈的时间。

单名工程师承担相同工程范围时，纯工程周期约 32–40 周，设计与测试仍需投入。若要求更早可用，先发布 S1 的动效与参考页 alpha，再分批扩展组件；最终 v1.0 范围维持明确。

### 1.1 责任分配

| 角色 | 主要责任 |
| --- | --- |
| 维护负责人 | 版本、公共 API、依赖、范围和发布决定 |
| 组件工程师 A | Token、基础 API、LoadingSequence 与复杂交互 |
| 组件工程师 B | 通用组件、页面组合、文档/Registry 生成与消费集成 |
| 设计负责人 | 参考动画对照、视觉 Token、信息层级、状态与响应式评审 |
| 测试负责人 | 行为矩阵、辅助技术、消费项目、浏览器与发布验证 |

同一人可以兼任多个角色，实际投入影响日历周期。AI 可协助实现、补文档和执行检查，估计按可审查的人类工程工作量制定。

### 2.1 S0：先证明工程链成立

1. 确认产品名，读取实际首个消费项目约束；查询 npm 包名与账号权限，暂时缺少账号时先采用本地 tarball。
2. 锁定 Node 活跃 LTS、pnpm、React 19、TypeScript、Base UI、Storybook/Vite 的真实兼容组合。
3. 建立单包 workspace、ESM 出口、TypeScript strict、CSS 命名空间与显式样式导入。
4. 用一个简单 Button 证明类型导出、样式、ref 和 npm tarball 消费可以工作。
5. 建立 Token 最小生成与校验，首先覆盖颜色、尺寸、时长、引用；增加类型时同步增加明确失败用例。
6. 建立文档壳、一个 Story 与一个交互检查，记录 package/manifest/源码版本策略。

交付记录包括版本清单、干净构建输出、tarball 文件清单、Vite 消费截图和已知限制。可用版本、包名和工具配置在此阶段从建议转为已验证事实。

### 2.2 S1：优先完成标志性加载序列

按以下顺序逐项提交和验证：

1. 提取 SVG 几何、色彩、时间与缓动基线，建立原版动画对照演示。
2. 实现 LoadingMark：三角/横线正向绘制、不同速度的双环、完整等待形态。
3. 实现 LoadingSequence：标签、进度扫光、反向绘制、scale/blur/opacity 解构、内容接续。
4. 接入 taskId、loading/ready/error、最短展示策略、提前完成时从当前描边撤回。
5. 完成取消、重复 ready、任务替换、卸载、Strict Mode 和减少动画边界。
6. 在演示中提供原版/精修版、慢速、重放、等待、提前完成和失败按钮。
7. 完成 G0 其余组件，将动画组合到访问状态页和局部 Panel 两种场景。
8. 完成字体、色彩、长内容和纵向滚动修正，形成第一份视觉与交互基线。

首个动效里程碑验收重点是用户认可的三个特征：SVG 的建立与撤回清晰，多元素时序有层次，解构与主内容交接自然。API 与性能调整围绕这三个特征展开。

### 2.3 S2：完成可操作的通用 UI

优先完成 Field 与原生输入，再完成选择控件、浮层、导航和表格。一个组件族完成后同时交付示例、用途说明与关键检查，避免批量生成只有默认态的组件。

设置表单覆盖字段错误、中文输入法、保存失败与草稿保留；筛选列表覆盖初次加载、空数据、筛选为空、请求失败、分页、详情抽屉和窄屏。用两个主题作用域打开嵌套浮层，验证 Portal、层级、滚动锁定和焦点恢复。

### 2.4 S3：完成 AI 用户控制链

采用固定的本地演示数据驱动消息分段、任务失败、取消与重试，保证不接模型服务也可回归。另由业务项目提供至少一次真实模型流接入，验证真实状态映射和停止行为；模型调用与凭据留在业务应用。

产物审核覆盖预览、修改、确认、执行中、执行失败和 revision 冲突。SourceList 与 ToolResult 使用脱敏的真实结构样本，并覆盖缺失来源和长输出。

### 2.5 S4：完成 AI 资料与安装闭环

1. 从公共导出、Props、JSDoc、用途说明和可编译示例生成资料。
2. 校验 schema、路径、示例 ID、组件名、Token、版本和源码链接。
3. 生成 5 个 Registry block，锁定同批基础包版本。
4. 从 tarball 与本地 Registry 分别安装到干净项目，完成原有文件冲突和升级演练。
5. 通过现有兼容 MCP 工具检索与读取 Registry，验证实际客户端可用的能力。
6. 执行 12 项 AI 任务集，记录模型、提示、版本、失败日志和修正次数。

### 2.6 S5：试点、发布与维护交接

至少选择两个不同结构的真实使用场景：一个偏表单/数据操作，一个偏加载序列/AI 任务。可以位于同一个业务系统的不同模块，由真实接入方使用发布包，避免仅在仓库内部路径下验证。

试点先固定 RC 版本，完成接入问题修正和迁移说明，再冻结 1.0 API。首次公开发布前明确 npm 名称与权限、正式静态文档/Registry 地址、源码许可证及参考素材权利。许可证建议优先评估 MIT，最终由项目权利人决定并保留依赖声明。

## 3. 质量验证体系

### 3.1 按风险设置检查

| 层次 | 工具与方式 | 主要验证内容 |
| --- | --- | --- |
| 类型与静态 | tsc strict、ESLint、CSS/Token 约定检查 | 公共类型、非法参数、导出、依赖方向和样式污染 |
| 纯逻辑 | Vitest 或已有 Node 测试 | Token 引用、版本资料、状态选择、取消与序列标识 |
| DOM 交互 | Testing Library / Story 交互 | label、键盘、输入、受控状态、错误与回调 |
| 浏览器 | Playwright | Clipboard、浮层定位、滚动、视口、动画、真实布局和水合 |
| 可访问性 | axe + 人工键盘与屏幕阅读器 | 自动问题、焦点流程、播报、阅读顺序和系统偏好 |
| 视觉 | 固定环境截图 + 加载动画录屏/连续帧 | 状态差异、材质、文字与完整时间序列 |
| 消费 | tarball 安装 + Registry 源码安装 | package exports、CSS、依赖、类型、SSR 与升级 |

每项有分支或状态转换的非平凡行为至少保留一个能捕获回归的可运行检查；高风险路径按必要边界扩充。纯样式小组件通过代表性 Story 和截图验证，测试用例避免照搬实现细节。

Storybook 可访问性插件可用于开发和 CI，自动检查之外仍保留人工验证。[Storybook 可访问性测试](https://storybook.js.org/docs/writing-tests/accessibility-testing)

### 3.2 重点行为用例

| 对象 | 用例 |
| --- | --- |
| LoadingSequence | 提前/正常/长时 ready，重复 ready，新 taskId，错误重试，卸载，减少动画中途改变，回调恰好一次 |
| CopyButton | 写入成功、用户拒绝、API 缺失，结果只在成功后显示成功态 |
| Dialog/Drawer | 打开焦点、Tab/Shift+Tab、Escape、遮罩关闭规则、关闭后恢复、嵌套 Popover、滚动锁定恢复 |
| Field/输入 | label、description、error 关联，受控/非受控，禁用、必填、中文输入法 |
| Select/Combobox | 方向键、检索、无结果、选项异步更新、值消失的显示策略 |
| Table/列表 | 空数据与筛选为空、稳定 row key、排序语义、分页变化、长单元格、选中操作 |
| Conversation | 用户位于底部时跟随，上翻时保持位置，历史插入后阅读位置稳定 |
| Confirmation | 连续激活、失败恢复、过期 revision、拒绝、业务回调错误 |
| 主题 | 嵌套主题浮层继承、密度变化、实色降级、forced-colors |

### 3.3 视口与辅助技术

发布前覆盖 360×800、390×844、768×1024、1280×720、1440×900、1920×1080。另设 667×375 小高度、200% 缩放与相当于 320 CSS px 宽度的重排场景，验证底部操作和内容始终可达。

通用页面无非预期横向溢出；数据表和代码等需要二维布局的内容在独立容器滚动。长中文、英文长单词、长 ID、较长按钮标签和键盘焦点均进入样张。

人工辅助技术基线为 Windows 的 NVDA + Edge/Firefox，以及 macOS/iOS 的 VoiceOver + Safari；可用设备不足时相应项明确标记待验收，并在宣称支持前补齐。Playwright WebKit 用于持续回归，真实 Safari/iOS 仍用于正式兼容性验收。适用 WCAG 2.2 AA 项目逐项记录，不能把一次 axe 通过等同于全面符合。[WCAG 2.2](https://www.w3.org/WAI/WCAG22/quickref/)

## 4. 性能预算

以下为 S0/S1 建立测量基线后的初始目标，调整时记录原因与消费影响。所有结果必须说明设备、OS、浏览器版本、构建模式、数据规模和测量次数。

| 项目 | 初始目标 | 测量口径 |
| --- | --- | --- |
| Button 子路径 | ≤ 5KB gzip 增量 JS | 生产构建相对空 React 页面，排除 React 本身，计入实际引入依赖 |
| LoadingSequence | ≤ 15KB gzip 增量 JS | 包括自身与引入的辅助模块，不含 React；样式另计 |
| Dialog 组合 | ≤ 35KB gzip 增量 JS | 包括 Base UI 对应依赖，独立消费入口 |
| 全部基础 CSS | ≤ 30KB gzip | Token + G0/G1，分别记录 motion 和 AI 附加 CSS |
| LoadingSequence 稳定性 | 退出后自身活跃动画/计时器/RAF 为 0 | 连续进入退出与卸载检查，不统计宿主动画 |
| 动画流畅性 | 60Hz 基准设备下，p95 帧间隔初始目标 ≤ 20ms；无可归因于序列的 >50ms 长任务 | 1280×720、1920×1080 各重放至少 5 次，首轮预热单独记录 |
| 列表操作 | 100 行×8 列时，排序/切页反馈 p95 < 100ms | 排除网络等待，固定生产构建和设备 |
| 消息更新 | 100 条历史消息、当前 20KB 文本、20 次/秒分段更新可持续操作 | 输入与滚动录制，定位 >50ms 长任务 |

没有达到目标时先依据轨迹定位根因：模糊范围、重复渲染、过大依赖或布局失效。全屏 blur 改为局部 blur、进度 left 改为 transform、消息分段合并等都需要保留真实效果对照。触发实际规模上限后再引入虚拟化和复杂缓存。

## 5. 拟建质量脚本

以下脚本名是工程目标，当前仓库尚未实现。S0 将可用命令落入 package.json；每增加一种产物，补齐对应检查。

| 脚本 | 承诺内容 |
| --- | --- |
| `pnpm typecheck` | 所有包、示例、Registry 源码和 Props 用例进行语义类型检查 |
| `pnpm lint` | 代码与可访问性规则、直接相关文案和格式 |
| `pnpm test` | 逻辑和 DOM 交互回归 |
| `pnpm test:browser` | 核心组件与页面组合的浏览器行为 |
| `pnpm test:motion` | 真实序列播放、受控关键帧、取消与减少动画 |
| `pnpm test:a11y` | 代表性 Story 的 axe 检查，人工项另外记录 |
| `pnpm build` | 构建包、声明、CSS 与静态资料 |
| `pnpm build:docs` | 静态文档与预览产物 |
| `pnpm build:registry` | 生成 Registry JSON，填入源码和实际版本 |
| `pnpm check:artifacts` | 核验 exports、指令、文件清单、版本、链接、schema 与依赖 |
| `pnpm check:consumers` | 从打包产物安装并验证 Vite/Next 消费项目 |
| `pnpm check:ai` | 校验资料、编译固定示例并汇总已执行的 AI 任务结果 |
| `pnpm check` | 按顺序运行本版本已定义的必需质量链 |

PR 的快速链执行类型、静态、相关逻辑与组件交互、资料一致性；公共基础变更扩大到受影响组件。发布链执行完整构建、浏览器、动效、消费与静态文档验证。受影响关系来自真实 import 与公共出口；缓存仅复用相同输入的结果。

AI 服务调用结果单独记录，以固定任务和模型版本复现；离线 CI 保持类型、示例与资料检查可运行。尚未实现的命令和未执行的环境不能在报告中显示为通过。

## 6. 分发验收与发布流程

### 6.1 消费验证

| 场景 | 必须证明 |
| --- | --- |
| Vite 新项目 | 从 tarball 安装，导入 Button、LoadingSequence 和 CSS，构建并实际使用 |
| Next 消费项目 | 服务端展示组件与客户端交互边界正确，无水合警告；样式与 Portal 工作 |
| 与现有样式共存 | 有全局 reset、有 Tailwind 与无 Tailwind 的场景，组件与宿主互不意外覆盖 |
| Registry 安装 | 所有文件和依赖完整，基础/motion/AI 样式说明准确，路径别名正确 |
| 源码升级 | 本地修改得到保留，新旧配方差异可审阅 |
| 版本资料 | npm、Token、manifest、Registry、文档与例子对应同一个 release |

这些消费项目使用生成的包，避免 workspace 链接掩盖漏文件、错误 exports 或隐藏依赖。

### 6.2 发布步骤

1. 完成版本变更说明与兼容性评估，确认所有必需验收项。
2. 从干净提交生成 npm tarball、文档、源码资料与 Registry；记录提交和文件校验值。
3. 检查包内容：仅包含声明的产物、必要源码、说明与许可证，排除凭据、个人路径和样本隐私信息。
4. 将候选版本作为 RC 分发，在两个实际使用场景完成消费验证。
5. 发布正式 npm 版本，再发布引用该版本的不可变静态 Registry 与文档。
6. 最后更新当前稳定入口，执行公开地址的安装烟雾检查并记录结果。

正式发布属于后续实施动作，当前任务仅生成本地方案。发布凭据放在受控 CI secret 中，文档只保存配置名和操作步骤。

### 6.3 回退与维护

旧版本的包、Registry 与文档保持可获取。发布异常时将当前稳定入口指回已验收版本，消费项目锁回上一版本；已经发布的错误包通过修复版本与弃用提示管理。模型缓存按版本刷新，防止旧组件目录继续推荐错误 API。

0.x 阶段仍记录所有破坏性变更；1.x 阶段采用语义化版本，新增兼容能力使用 minor，修复使用 patch，公共 API 或 Token 的破坏性调整使用 major。视觉改动同样提供前后对照与受影响范围。

维护负责人定期检查依赖更新、组件使用反馈、AI 任务退化和可访问性问题。每项公共能力需有明确维护者；新增组件先查现有组合，首次业务专用结构可以保留在配方中，第二个真实场景再评估提升。

## 8. 首周可直接执行的任务

## 9. 高影响风险与处理

| 风险或假设 | 影响 | 处理与触发条件 |
| --- | --- | --- |
| 仅用安全终端页面推导全部组件 | 表单和数据场景可能只有外观 | S2 用真实设置/列表任务验证，v1.0 前完成两类试点 |
| 完整动效与任务耗时不同步 | 额外等待或退出跳变 | 最短展示显式配置，提前就绪从当前进度撤回，单独验收 |
| 全屏 blur 和多层材质 | 中低性能设备卡顿 | S1 测量，超预算时改局部 blur，保留同一视觉叙事 |
| 柔和颜色直接用于正文和状态 | 信息难辨认 | 建立成对语义色并检查真实叠加背景 |
| npm 与源码分发双重维护 | 升级失配和文档漂移 | v1.0 基础实现只维护 npm 真源，Registry 分发组合；同批生成版本资料 |
| 组件规模与人员不匹配 | 完整首版延期 | alpha/beta/RC 分段交付，按真实投入调整周期 |
| AI 自动生成的外部内容 | 不安全链接、不可控动作或失效确认 | 内容按不可信输入处理，确认绑定版本，服务端负责实际执行 |
| 发布账号、域名与素材权利未明确 | 无法正式对外发布 | 本地 tarball 先行，S5 前落实负责人和发布条件 |

当前最重要的决策是把 **加载动画的完整视觉叙事**作为第一验收对象，同时用 **真实任务状态和跨场景复用**约束实现；完整首版的工期依赖 **实际工程投入与试点反馈**，阶段性产物和可重复的验收证据是控制范围与质量的基础。
